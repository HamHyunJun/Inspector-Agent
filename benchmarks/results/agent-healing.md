## 측정 방식

- 대상: `apps/playground` 임시 복사본 (375px, 오버플로우 4건). 정답용 결함 중 가려짐·포커스 이탈은 이 실험에 넣지 않았습니다.
- 판정: 같은 뷰포트 재측정에서 대상 결함이 사라지고 새 결함이 없을 때만 통과, 실패하면 자동 롤백 후 재제안.
- 경로: 실행 중인 MCP 서버는 다른 대시보드를 가리켜서, MCP 도구가 호출하는 대시보드 REST API(`/api/defects/:id/context`, `/api/patches`, `/api/patches/:id/apply`)를 직접 호출했습니다. 컨텍스트 읽기, 소스 확인, 편집 작성은 에이전트가 하고 적용과 재측정은 대시보드가 합니다.
- 매 실행 전에 복사본을 원본 상태로 되돌리고 스캔부터 다시 했습니다.

## 해석 시 주의

- 같은 세션의 같은 에이전트가 3회 반복한 것이라 실행 간 독립성이 없다 (직전 실행과 이전 대화의 지식을 가진다)
- playground 소스에는 결함 원인을 알려 주는 주석이 있다
- 실패 후 재제안 경로는 이번에는 한 번도 실행되지 않았다 (모든 결함이 첫 시도에 통과)
- 따라서 이 수치는 "에이전트가 일반적으로 이 정도 고친다"는 추정이 아니라, 제안 → 적용 → 재측정 파이프라인이 에이전트 패치와 함께 끝까지 동작함을 보여 주는 기록입니다. 성공률의 의미 있는 비교(모델별, 컨텍스트 유무별)와 재제안 경로 검증은 독립된 실행(새 세션, 원인 주석 제거, 더 어려운 결함)이 필요합니다.
